01 Flagship

NBA Analytics Pipeline

111,285 player-game rows across five seasons, queryable two ways: PostgreSQL for the app and Athena for analysis, with the two checked against each other.

Architecture

  1. Extract. Python pulls player game logs one season at a time, with retries, and keeps the raw CSVs unchanged.
  2. Transform. pandas derives the season from the source ID so any season loads, joins team and player names, handles zero-attempt shooting percentages, and runs validation asserts.
  3. Serve. Recent seasons are upserted into PostgreSQL on Amazon RDS with INSERT … ON CONFLICT DO UPDATE, so reruns are safe. FastAPI reads it through DATABASE_URL and falls back to local PostgreSQL.
  4. Analyze. Raw and processed CSVs go to S3 with boto3. Athena queries all five seasons through a Glue Data Catalog table whose definition is managed in Terraform.
  5. Validate. Athena results for the seasons held in both stores are checked against PostgreSQL.

Not done yet The daily refresh isn’t scheduled. An EventBridge rule exists but is disabled because the stats API times out from AWS, so the pipeline runs by hand for now.

02 Scheduled pipeline

NFL Wide Receiver Rankings Pipeline

Scores every wide receiver each week and stores the rankings in Supabase. A GitHub Actions job runs it every Tuesday and writes a week only after every game has a result.

Architecture

  1. Ingest. Weekly player stats and receiving drop stats come from nflverse Parquet release files, and schedules and results come from CSV.
  2. Check. A completeness gate skips any week with unfinished games. Table reads page past the 1,000-row API cap instead of silently truncating, and ambiguous player names log a warning.
  3. Rank. A tiered points formula produces weekly rankings, season averages, and next-week predictions.
  4. Store. Raw rows are uploaded as Parquet, and players, weekly stats, and rankings are upserted into Supabase (PostgreSQL).
  5. Run. GitHub Actions runs it on a weekly schedule or on demand. Every script takes --dry-run, which fetches and scores but writes nothing.

Note The pipeline started in Python and now runs as a TypeScript port. Tests check the port against outputs saved from the original Python code.

03 API

Payment Reconciliation API

Classifies every invoice as paid, partly paid, unpaid, or overpaid and flags payments that match no invoice, backed by 34 automated pytest tests.

Architecture

  1. Store. A MySQL schema owned by SQL files. Payments deliberately have no foreign key to invoices, so unmatched payments can still be stored.
  2. Reconcile. SQL LEFT JOINs and INNER JOINs match payments to invoices. Money stays DECIMAL end to end.
  3. Serve. FastAPI endpoints import payments, invoices, and contracts, and return the reconciliation report and its exceptions.
  4. Test. 34 pytest tests cover seed row counts, the answer key for twelve join queries, and the API, with the original CSV version kept as a regression check.
